Architecture Note

没有用任何 Agent 框架。
它自己写了一个。

JobCopilot 的 Agent 层是一个手写的 tool-calling Runtime：直接用 httpx 调 OpenAI 兼容的 /chat/completions，自己做工具注册、循环编排、SSE 流式和向量记忆。整个 agent 包 1,709 行 Python，没有 LangChain、LlamaIndex、AutoGen 或任何 agent 依赖。

agent 包 1,709 行 工具 20 + 16 模型 deepseek-chat 依赖 0 个 agent 库
Verdict

项目的 agent 框架是自研 tool-calling Runtime——位于 backend/app/agent/，基于 OpenAI function calling 协议手工实现，不依赖任何第三方 agent 框架。

它的核心抽象只有一个：Tool(name, description, parameters, handler) 数据类 + 按角色分组的 TOOLSETS 字典。Runtime 的全部逻辑就是「调模型 → 有 tool_calls 就执行 → 结果回喂 → 再调模型」的 for 循环，上限 8 轮。

03

执行循环

这是整个框架最核心也最朴素的部分。没有 planner、没有 graph、没有 state machine，就是一个最多跑 8 次的 for 循环。每次迭代调一次流式模型，把 tool_calls 增量按 index 拼接完整，执行后把结果作为 role: tool 消息塞回 messages，进入下一轮。

1
落库用户消息
写入 AgentMessage(role="user")；若会话标题还是「新会话」，用首条输入前 24 字符命名。
2
组装 messages
_build_messages：system prompt + （首轮时）长期记忆检索注入 + 最近 24 条历史，并剔除残缺的 tool 轮避免上游 API 报错。
3
流式调模型
chat_completion_stream 逐 chunk 产出 {"content", "tool_calls"}；content 实时 yield 成 token 事件给前端。
4
分流
没有 tool_calls → 落库 assistant 消息，yield done 结束。有 → 拼接完整调用（补 id），落库并追加到 messages。
5
执行工具
逐个 tool_start → await tool.handler(db, user, **args) → tool_end（结果截 600 字给前端）。异常被捕获并 rollback，错误 JSON 回喂模型而不是炸掉循环。
6
回喂下一轮
工具结果序列化（上限 6,000 字符）写入 AgentMessage(role="tool") 并 append 到 messages，进入下一次迭代。
7
兜底
8 轮仍未结束 → 落库「本轮工具调用次数已达上限」的提示并 yield done。

几个值得注意的工程细节

  • 历史修复：_build_messages 会丢掉开头孤立的 tool 消息，并只保留「assistant.tool_calls 里的每个 id 都有对应 tool 结果」的完整轮次——这是踩过 OpenAI 协议报错之后才会写的代码。
  • 工具异常不中断：_execute_tool 捕获所有 Exception，先 rollback() 再把错误当结果回喂，注释写明「避免后续 commit 抛 PendingRollbackError」。
  • 流式与 SSE 解耦：Runtime 是纯 AsyncIterator[dict]，路由层只负责把它包成 data: ...\n\n。对谈模块 duel.py 复用了同一套事件结构。
  • 独立 Session：SSE 生成器里新建 SessionLocal()，不共用请求级 DB 会话，避免流式期间的连接生命周期问题。
04

工具层

工具就是一个 @dataclass，四个字段，没有基类、没有装饰器魔法、没有 schema 自动生成——JSON Schema 是手写的，用一个小 helper obj(properties, required) 简化。

@dataclass
class Tool:
    name: str
    description: str
    parameters: dict          # 手写 JSON Schema
    handler: Handler             # (db, user, **args) -> Awaitable[Any]

    def schema(self) -> dict:  # 转成 OpenAI tools 格式
        return {"type": "function", "function": {...}}

TOOLSETS = {"seeker": SEEKER_TOOLS, "employer": EMPLOYER_TOOLS}  # 20 / 16

权限不在 Runtime 里判断，而是在工具层收口：每个 handler 第一个动作就是 db.scalar(select(Resume).where(Resume.user_id == user.id)) 这类带 user 过滤的查询，模型拿不到别人的数据。TOOLSETS[agent_type] 按角色分组，求职者会话根本看不到 create_job。

求职者 · 20 个工具

  • 简历：get_my_resume、suggest_resume_improvements
  • 岗位：search_jobs、get_job_detail、match_jobs_for_me、apply_to_job
  • 投递：get_my_applications、list_my_pipeline
  • 面试：start_mock_interview、create_mock_interview、submit_interview_answer、get_interview_report、respond_interview_invite
  • Offer / 入职：respond_offer、confirm_onboarding、abandon_onboarding
  • 订阅与通知：create_subscription、list_unread_notifications
  • 记忆：save_memory、search_memory

招聘方 · 16 个工具

  • 岗位：generate_job_description、create_job、update_job、list_my_jobs
  • 候选人：list_candidates、screen_candidate、rank_candidates
  • 流程：update_application_status
  • 面试：create_interview_invite、cancel_interview_invite、complete_interview_invite、get_candidate_interview_report
  • Offer / 入职：create_offer、record_onboarding_result
  • 记忆：save_memory、search_memory

表 3 · 两套工具集。两侧都含 save_memory / search_memory，所以按角色去重后共 34 个不同工具。

另一个设计选择：工具 handler 直接就是 service 层函数（job_service、application_service 等）的薄包装，工具不绕过业务规则。写操作类工具（apply_to_job、create_offer）在 system prompt 里被要求「必须用户明确确认后才调用」，但这只是 prompt 约束，Runtime 层没有二次确认机制。

05

记忆

两层记忆，都很轻。

层存储机制
短期（会话）AgentMessage 表每次取最近 24 条（HISTORY_LIMIT），含 tool_calls 与 tool 结果；超出的直接丢，无摘要压缩
长期AgentMemory 表save_memory 先 embedding，与已有记忆余弦相似度 > 0.95 视为重复则更新；search_memory 全量取出该用户记忆按相似度排序取 top_k

表 4 · 两层记忆。向量以 JSON 列存在 SQLite，用 app.utils.cosine_similarity 在 Python 里算，没有向量数据库。

长期记忆的注入时机很克制：只在会话首轮（该 session 还没有任何 assistant 消息时）用用户首句去检索 top-5，拼进 system prompt 的「已知用户体验/偏好」段。之后不再自动注入，要靠模型主动调 search_memory。代码注释里写这是「D11 演示彩蛋的可靠实现」。

06

双 Agent 对谈

duel.py 是README 里提到的「候选人 Agent 与招聘方 Agent 自主对谈」。它是 runtime.py 之外的一层纯演示编排，文件头就写明「不落库、不污染正式会话」。

  • 编排方式：stream_duel 按轮次让 seeker、employer 交替发言，每轮各自调 _run_turn（内部同样是最多 3 次工具调用的循环）。
  • 上下文：不用共享 messages。每个 agent 每轮都重新 _build_messages，把累积的 transcript 映射成自己的 assistant/user 轮次，并在 system prompt 里塞入岗位 JSON 和简历 JSON。
  • 工具白名单：DUEL_TOOLS 只开放只读工具——seeker 拿 3 个，employer 拿 3 个，且 _execute_tool 会先校验 name in DUEL_TOOLS[agent_type]，防止对谈过程产生投递、改状态等副作用。
  • 收敛：最后一轮 employer 被 final=True 要求「收束并给出结论」，每轮发言截 1,600 字符。

这是一个 hand-rolled 的多 agent 协作：没有消息总线、没有共享状态、没有 supervisor。代价是两个 agent 的「对话」其实是各自把对方的话当 user 消息重放，不存在真正的共享上下文。

08

取舍与风险

对一个「学习项目、重点是自研 Runtime」的仓库来说，这些取舍是合理的——但有几处如果往生产推会变成真实问题。

项现状评价
无外部依赖只有 httpx + FastAPI对学习项目是优点：循环逻辑全在 222 行里可读完，换模型供应商只改 .env
历史无压缩硬截 24 条长会话会丢失早期上下文；没有 summarization 或 token 计数
记忆检索 O(n)全量取该用户记忆再排序单用户记忆条数少时无所谓，上千条后会明显变慢；无向量索引
写操作仅 prompt 约束「用户确认后再调用」Runtime 层没有 human-in-the-loop 门禁，模型误调用会直接写库
工具循环上限8 轮硬上限复杂任务（先搜岗位再比对再投递）可能触顶，兜底提示较笼统
无 trace / 评估只有 SSE 事件没有 token 成本统计、调用链追踪或回归评测集
