Architecture Decision · JobCopilot

为什么不用 LangChain、LlamaIndex 或 AutoGen

Agent 执行循环由项目自己实现，只依赖 OpenAI 兼容协议和 httpx。这不是对框架的否定，而是学习目标、工具形态和复杂度预算共同决定的取舍。

日期
2026-11-25
依据

01

结论

JobCopilot 的 Agent 不是从零发明协议，而是把 OpenAI function calling 的标准循环写在 backend/app/agent/runtime.py 里——整个执行循环 222 行，LLM 适配层 149 行，工具注册器 1290 行。框架被砍掉的理由可以压成三句：

  1. 学习价值是第一验收标准。开发文档把「自研 Agent Runtime」列为学习目标第 1 位。引入 LangChain 等于把这个目标外包给第三方库，项目就失去了存在理由。
  2. 需要的原语极少。两个 Agent 共用一条 ReAct 式工具循环，底层是标准 function calling。LangChain 的 Chain / Retriever / Memory 抽象、LlamaIndex 的索引体系、AutoGen 的多 Agent 会话协议，对本项目都是额外概念税。
  3. 工具就是后端 service 函数。权限、事务、参数校验都要贴着 SQLAlchemy session 和当前用户走。框架的工具基类、Runnable 接口和回调栈会让这条路径变绕，排错时多穿一层。

自研不等于重造所有轮子。向量检索用 numpy 暴力余弦，简历解析用 pdfplumber / python-docx，模型调用走 OpenAI 兼容 HTTP——这些成熟件都留着。被砍掉的只是编排层框架。

02

决策出处

这条决策写在 docs/开发文档.md 决策记录 D4，2026-11-20 定稿：

编号决策项结论
D1 项目性质 学习项目，验收 = 学习价值 + 可演示性不做真实上线，不以市场指标验收
D4 Agent 深度 自研 tool-calling Agent Runtime（不用 LangChain / LangGraph）向 multi-agent 伸手但不做；双 Agent 对谈作为彩蛋另计
D7 LLM 接入 DeepSeek deepseek-chat，OpenAI 兼容适配层模型可配置切换，不改业务代码

D4 明确点名 LangChain / LangGraph。LlamaIndex 和 AutoGen 虽未写进表格，但被同一条逻辑覆盖：它们和 LangChain 一样是编排层框架，引入即替代自研 Runtime 这个学习目标。

开发文档 §7.1 同时规定了自研的边界——工具就是后端 service 函数、单轮工具调用有上限、异常回喂不炸循环、权限在工具层收口。这四条约束反过来证明了为什么框架不合适：框架的抽象点（Chain、Agent Executor、Group Chat）和这些约束不在同一个层面上。

03

自研 Runtime 长什么样

Agent 相关代码全部集中在 backend/app/agent/，没有任何第三方 agent 依赖：

backend/app/agent/
├── runtime.py     222 行   执行循环 + SSE + 历史清洗
├── tools.py     1 290 行   工具注册器 + 双侧工具清单
├── duel.py       235 行   双 Agent 自主对谈编排
├── prompts.py    约 130 行   系统 prompt
├── memory.py      53 行   结果序列化 / 长期记忆读写
└── __init__.py

backend/app/llm/
└── client.py     149 行   OpenAI 兼容 chat / embedding / 流式
行数统计自当前工作区文件，非运行时估算。

3.1 执行循环

AgentRuntime.stream() 是唯一的主循环。它不做规划、不建任务图、不搞反思，只做教科书式的 tool-calling：

1
组装 messages
system prompt + 最近 HISTORY_LIMIT = 24 条历史 + 本次输入。会话首次对话时先检索一次长期记忆注入 prompt。
2
带 tools 调 LLM
工具 schema 来自注册器，格式就是 OpenAI function calling 的 {"type":"function", ...}。
3
有 tool_calls 就执行
逐个调用注册的 handler，结果以 role: tool 追加，回到第 1 步。流式 token 与工具开始 / 结束事件同步推给前端。
4
纯文本则收尾
assistant 消息落库，yield done。若已达 MAX_TOOL_ROUNDS = 8 仍未收尾，写入兜底文案结束。

3.2 工具就是 service 函数

工具不是框架里的 BaseTool 子类，而是一个 dataclass：名字、描述、JSON Schema 参数、一个 async (db, user, **args) 形状的 handler。Agent 和 REST API 调用的是同一层业务代码。

权限在这里收口：handler 第一个业务参数就是当前 User，Agent 永远只能操作本人资源，不依赖 prompt 自觉。求职者 Agent 与招聘方 Agent 各持一份工具清单，敏感动作（接受 Offer、推进流程状态）在描述里写明「需用户明确表态」。

3.3 LLM 适配层

llm/client.py 用 httpx 直写 OpenAI 兼容协议：非流式 chat_completion、流式 chat_completion_stream（手工解析 SSE）、embed_texts 批量向量化。chat 与 embedding 各自独立配置 base_url / api_key / model，换供应商只改 backend/.env。

这就是项目里唯一的「框架替代品」——一个 149 行的协议适配器，而不是一个 Agent 框架。

3.4 双 Agent 对谈

duel.py 是招聘方 Agent 与候选人 Agent 的自主对谈彩蛋。它没有用 AutoGen 的 Group Chat，而是 235 行手写编排：双方各持受限只读工具集，交替发言，最后一轮强制招聘方给出是否推进面试的结论。对谈不落库、不产生投递等副作用。

04

三个框架为何不引入

4.1 LangChain / LangGraph

D4 点名淘汰。理由不是「LangChain 不好」，而是它解决的问题本项目不存在，它带来的成本本项目扛不起。

维度LangChain / LangGraph 会带来什么JobCopilot 实际需要什么
抽象层级 Chain、Runnable、Retriever、Memory、Agent Executor、StateGraph 一条 function calling 循环 + 一张工具表
工具接入 继承 BaseTool 或包 @tool 装饰器，走框架的调用协议 直接持有 SQLAlchemy session 和 User 的 service 函数
流式输出 Callbacks / astream_events 事件体系，再映射到自己的 SSE 循环里原生 yield token / tool_start / tool_end
学习价值 学会一套框架 API，框架升级后可能重来 吃透 tool-calling、消息协议、历史清洗、权限收口
依赖面 langchain-core + 集成包 + 版本变动频繁 requirements.txt 里没有任何 agent 包

LangChain 的价值在快速拼装通用 RAG / Agent demo，或在成熟产品里复用生态集成。本项目两者都不占：不是 demo 拼装（要的就是手写循环），也没有几十个第三方工具要接（工具就是自己的 service）。LangGraph 的状态图更适合多角色、有分支回环的复杂工作流；这里的双 Agent 对谈只是一个固定的交替发言编排，用 duel.py 的 for 循环就写完了。

4.2 LlamaIndex

LlamaIndex 的核心是数据框架：Document / Node / Index / Retriever / Query Engine，强项是把异构数据源建成索引再做 RAG。JobCopilot 的检索场景和它错位：

  • 向量召回的对象是结构化简历 vs 结构化 JD，不是非结构化文档切块。简历已经过 LLM 抽取成 JSON，匹配走「向量召回 → 规则精排 → LLM 解读」三段式，规则打分占大头（技能 50 + 年限 20 + 地点 15 + 薪资 15）。
  • 向量存 SQLite JSON 字段，numpy 暴力余弦取 Top-20。这个量级（种子数据 322 个岗位）用不上 FAISS / Milvus，更用不上 LlamaIndex 的索引抽象。
  • 如果哪天要接 PDF 知识库、多文档问答，LlamaIndex 才是对口的工具。现在的「PDF → 结构化档案」是抽取管线，不是检索管线。

4.3 AutoGen

AutoGen 的卖点是多 Agent 会话：Agent 之间互发消息、群聊、人机协作、代码执行沙箱。项目里唯一的「多 Agent」是 duel.py 的双方面谈，形态完全不同：

AutoGen Group Chat

为开放协作设计：多个 Agent 自主决定发言、互相互动、可接代码执行器与人类代理。

  • 发言权交给框架的 speaker selection
  • 消息总线、会话协议由库管理
  • 适合探索式、角色多的编排

duel.py 手写编排

为固定演示设计： seeker / employer 交替各说一轮，最后一轮招聘方必须给结论。

  • 发言顺序写死在 for 循环里
  • 工具白名单 DUEL_TOOLS 只放只读工具
  • 对谈不落库，不产生业务副作用

为一个彩蛋引入整个 AutoGen，依赖和概念都不成比例。开发文档 D3 / D4 的态度也是一致的：「向 multi-agent 伸手但不做」——对谈作为二期彩蛋实现，不把项目升级成多 Agent 系统。

05

自研要自己扛的脏活

不用框架不等于没有工程问题。下面这些点框架通常会替你挡一层，自研就得自己写。它们也正好是学习目标的一部分。

问题JobCopilot 的做法位置
工具死循环 单轮工具调用上限 8 次，超限写入兜底文案 runtime.py · MAX_TOOL_ROUNDS
工具异常 捕获后回滚事务，错误 JSON 回喂 LLM，不炸循环 runtime.py · _execute_tool
历史截断 取最近 24 条；剔除孤立的 tool 开头；丢弃缺少 tool 结果的不完整轮 runtime.py · _build_messages
流式 tool_calls 按 index 累积 name / arguments 分片，结束后再执行 runtime.py / duel.py / client.py
参数不合法 JSON 解析失败兜 {"_raw": ...}；TypeError 回喂「参数不匹配」 runtime.py · _safe_json / _execute_tool
权限越界 handler 强制注入当前 User，不靠 prompt 自觉 tools.py · 所有 handler 签名
上下文超窗 简单截断最近 N 条，不做摘要压缩 开发文档 §7.4 已知取舍
对谈副作用 对谈只用只读工具白名单，不落库 duel.py · DUEL_TOOLS

这些代码加起来不到三百行循环逻辑。框架能提供的是更通用的版本（摘要记忆、更聪明的重试、可视化 StateGraph）。本项目的选择是：先把这些脏活亲手写一遍，等真的撞到截断导致失忆、工具雪崩这类问题，再决定要不要借框架的解法。

06

代价与已知取舍

自研不是免费午餐。下面这些代价是真实存在的，开发文档里也如实记了一部分。

失去了什么影响当前态度
生态集成 接 Slack、Notion、各种 VectorStore 要自己写适配 本项目工具全是内部 service，暂无此需求
开箱记忆 / RAG 组件 长期记忆只有 save / search 两个工具，无摘要压缩 D11 有意做薄；超窗截断是已知取舍
可观测性 没有 LangSmith / Langfuse 开箱埋点 消息全落 agent_messages 表，SSE 可视化工具调用
多人协作协议 没有现成 Group Chat / Human-in-the-loop 组件 双 Agent 对谈手写编排， human 确认放在工具描述层
升级红利 框架新特性（如结构化输出流式、更稳的 ReAct）吃不到 模型能力主要通过 OpenAI 兼容协议直接享受
注意 自研的对象是编排层。模型协议、HTTP、向量计算、文档解析都用现成库。把「不用 agent 框架」理解成「什么轮子都自己造」是对这条决策的误读。
07

什么时候应该换

D4 说「后续开发不得静默更改；如需推翻，先更新本文档」。出现下面任一情况，才值得重新评估：

  1. 工具数量失控。双侧工具如果涨到几十个、开始接外部 SaaS，自己维护 JSON Schema 和 handler 注册会累，框架的工具生态开始有意义。
  2. 编排复杂到手写开始出错。需要条件分支、人工中断续跑、多角色动态发言、失败回滚整条链路——LangGraph 的 StateGraph 或 AutoGen 的会话协议此时才比 for 循环更可靠。
  3. 项目性质变了。从学习项目变成要交付的生产系统，学习价值不再是第一验收标准，团队熟悉框架时引入框架的性价比会反转。
  4. 检索需求变成真 RAG。要索引大量非结构化文档、做多源召回与重排，LlamaIndex（或同类）就该进入选型讨论，和 Agent Runtime 是两件事。

在这四种情况出现之前，自研 Runtime 是和项目定位最一致的选择：代码量可控、协议是标准的、每一条权限和截断规则都看得见。

一句话收束：这里不用 LangChain、LlamaIndex、AutoGen，是因为这个项目要学的就是那层循环本身，而它需要的编排又简单到不值得为之外聘一个框架。
