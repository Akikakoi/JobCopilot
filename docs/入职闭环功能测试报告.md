## 3. 测试目标

验证招聘流程从 Offer 到入职的完整闭环：

1. Offer 被接受后，投递自动进入 `onboarding`（待入职），并记录入职日期。
2. 候选人可以确认入职，也可以放弃入职。
3. 招聘方可以记录实际到岗结果：`hired`（已入职）或 `abandoned`（放弃入职）。
4. 入职日期、确认状态、到岗结果、备注能够在双端正确展示。
5. 状态流转、角色权限、站内通知与 Agent 工具行为正确。
6. 不破坏既有 Offer、面试邀约与投递流程。

## 4. 测试范围

### 4.1 已覆盖

- `Offer 接受 → onboarding → hired / abandoned` 状态流转。
- 入职日期继承、实际入职日期回填。
- 候选人确认入职、放弃入职。
- 招聘方记录已入职、放弃入职。
- 状态事件 `application_events` 写入。
- 站内通知 `onboarding_confirmed`、`onboarding_result`。
- 角色权限：候选人本人、岗位所属招聘方、无关用户。
- 非法操作：未接受 Offer、重复记录结果、放弃后再次确认、入职后重发 Offer。
- Agent 工具与 `list_my_pipeline` 下一步提示。
- 种子数据中的待入职与已入职演示记录。
- 既有 Offer / 面试邀约流程回归。
- 前端类型检查与生产构建。

### 4.2 未覆盖

- 浏览器端 E2E 与视觉回归。
- 多用户并发、压力与性能测试。
- 邮件 / 短信等外部通知。
- 旧数据库手工迁移的自动化测试（仅做代码审查）。
- Agent 提示词层面的“必须用户确认”约束，未做模型行为评测。

## 10. 缺陷与风险

### 10.1 阻断缺陷

无。

### 10.2 观察项与覆盖边界

| 编号 | 说明 | 影响 | 建议 |
|---|---|---|---|
| OBS-01 | 已存在数据库中的历史“已接受 Offer”记录不会自动改写为 onboarding | 旧演示数据看不到新入职入口；新流程不受影响 | 需要演示时使用 `seed --force` 重建（自动备份），或手工发起新 Offer |
| OBS-02 | 前端仅做类型检查与构建，未执行浏览器 E2E | 布局、交互与真实网络请求未自动化验证 | 发布前按第 11 节做一次人工冒烟 |
| OBS-03 | 旧库增量补列逻辑未写自动化测试 | 极端旧库结构下存在迁移风险 | 上线前用旧版 `jobcopilot.db` 副本启动一次验证 |
| OBS-04 | Agent 的“需用户确认”约束依赖提示词 | 模型可能绕过提示直接调用工具 | 重要操作仍建议前端二次确认；后续可加工具层审批 |

### 10.3 已知设计取舍

- 入职时间沿用项目现有 UTC naive 时间语义：前端把本地输入换算为 UTC 提交，读取时按 UTC 解析展示。
- 入职字段直接扩展 `applications` 表，不新增关联表。
- 入职阶段不允许通过看板拖拽改状态，必须走双端入职动作。

## 11. 人工冒烟建议

发布前建议用两个演示账号执行一次：

1. 招聘方对候选人发起 Offer，填写入职日期。
2. 求职者在「我的投递」接受 Offer，确认页面出现「待入职」和「确认入职」。
3. 求职者点击「确认入职」，招聘方铃铛收到通知。
4. 招聘方在候选人看板「待入职」列点击「记录已入职」，填写实际日期。
5. 双方页面均显示「已入职」，入职日期与结果一致。
6. 另起一条投递，验证求职者「放弃入职」与招聘方通知。

## 12. 验收结论

本次入职闭环功能的后端状态流转、权限控制、通知、Agent 工具与种子数据均通过自动化验证；前端类型检查与构建通过。未发现阻断缺陷，**建议通过验收**。浏览器端交互与旧库迁移属于本次未自动化覆盖的边界，建议按第 11 节补充人工冒烟。
